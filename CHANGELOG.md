# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

`## [Unreleased]` holds what has landed on `master` and not shipped yet: a pull request
writes its entries there, and the release the merge cuts moves the whole block under the
version it names — [docs/RELEASING.md](docs/RELEASING.md).

## [Unreleased]

### Changed

- **A setting admits more agents to the Codex tools.** The plugin's `PreToolUse` hook reads `CODEX_MCP_ALLOWED_AGENTS`, a comma-separated list of agent types, and lets each of them through beside `codex-mcp:codex` and a bare `codex` — an agent that drives Codex in its own context rather than through the subagent. Entries are trimmed and empty ones ignored; the hook runs in the environment of the session that spawned it, so the `env` block of a Claude Code settings file sets it. Every other caller, the head agent included, still gets `permissionDecision: deny`.
- **The `codex` subagent carries no tool but the five it proxies with.** Its `tools:` frontmatter names them under both the plugin spelling `mcp__plugin_codex-mcp_codex-mcp__*` and the bare `mcp__codex-mcp__*` a client configuring the server itself gives them, so the rule its prose states — read no file, run no command, write nothing — is what the agent holds rather than what it is asked to observe.

## [3.0.3] - 2026-08-30

### Added

- **The README shows what the tests reach.** `docs/coverage-badge.json` is a second shields.io endpoint document beside the fallow one, drawn from the Istanbul report the coverage run already writes: the share of measured lines the tests entered and the share of matched functions, over `src/` and `scripts/` and without the helpers a test drags into the report. Both shares are floored, so the badge never reads 90 for a tree the 90% gate would fail, and the colour reads the lower of the two — brightgreen at 95, green at the gate, red below it.

### Changed

- **A release measures its badges once and commits them once.** The `badge` job ran `bun run coverage` after the release was out, which was a second full suite per release and the one place a green release could still end red — it ran no `bun run build`, so the end-to-end tests that spawn the bundle timed out. The `check` job of `ci.yml` now writes both badge documents out of the coverage it already ran and answers with them as workflow outputs, and `promote` writes them down. Where a badge moved, `promote` commits the two documents as a child of the verified commit and moves the release branch to it, in the same `git push --atomic` that carries the tags; both tags name the verified commit, because the badge commit passed no matrix. Where neither moved the release writes no extra commit and pushes exactly what it pushed before.

## [3.0.2] - 2026-08-30

### Changed

- **The fallow analysis is a gate a commit has to pass, not a report it can walk past.** `bunx fallow` printed its findings and exited 0, so nothing it found stopped anything. The pre-commit hook now runs `bun run lint:fallow` — the suite under coverage, then the analysis over what it measured — and a finding stops the commit. Each analysis is called by name, because the combined `fallow` run exits 0 in every machine-readable format whatever it found. `.fallowrc.jsonc` carries what fallow enforces itself: CRAP 15, cyclomatic 10, cognitive 12, duplication 0.3%, and `minOccurrences: 3` so a reported clone group is a shape repeated three times rather than a pair — the percentage still counts the pairs, so that setting relaxes nothing. `.fallow-gate.jsonc` carries the three per-file ceilings fallow measures and leaves to the reader — 500 lines, 15 fan-out, 0.7 complexity density — which `scripts/fallow-gate.mjs` reads out of the report and fails on. The hotspot table `fallow health` prints — commits and churn per file — is information the reader acts on, not a ceiling. A file over a ceiling is split, or excepted by an entry naming the metric, the limit it is held to and the reason; an exception that no longer holds anything back fails the run.
- **CRAP scores were computed as if nothing were tested.** bun's lcov carries `DA` lines and the `FNF`/`FNH` totals and no per-function record, so the Istanbul report handed to fallow had an empty `fnMap` — and fallow matches functions through `fnMap` alone. Every function fell back to the static estimate, `cc + cc²`. `scripts/lib/lcov-istanbul.mjs` now rebuilds the `fnMap` from the TypeScript AST of each measured file, taking each function's hit count from the lowest measured line of its body; a function whose body carries no measured line is left out rather than reported as zero. Matched functions went from 0 to 647.
- **The README shows fallow's health score.** `bun run badge` writes `docs/fallow-badge.json`, the shields.io endpoint document the badge is drawn from, out of what `fallow health --hotspots --score` measured, and the `badge` job of the release workflow runs it over the commit each release shipped and pushes the file when the score moved. `--hotspots` and the whole git history are both conditions of the number being right: ten points of the score are the hotspot penalty, fallow weighs it only when asked and reads it out of the last six months of commits, and `bun run badge` refuses a report missing either rather than publishing a score ten points high.
- **Every file over a ceiling came apart.** `session/manager.ts` (4028 lines) is 23 modules under `session/manager/`, with `SessionRuntime` owning the state and each piece of behaviour a function over it. `app-server/protocol.ts` (1148) is seven modules under `app-server/wire/`; `server.ts` (1059) is the registration, the schemas and the error envelope under `mcp/`; `resources/register-resources.ts` (711) is nine under `resources/`; `app-server/client.ts` (624) is four under `app-server/client/`; `types.ts` (621) is five under `types/`; `tools/codex-setup.ts` is the shapes, the probe, the advice and the answer under `tools/codex-setup/`. Seven functions past the complexity thresholds came apart along the decisions they were making, and the four clone groups fallow reported are gone. Every entry point moved rather than staying as a facade, because the 500-line ceiling is cleared by the split itself and not by a forwarder left on the old path. No behaviour changed and no public name moved: an importer names the directory's `index.js`. The largest file is now 493 lines against 4028, and `tools/list` answers what it answered.

## [3.0.1] - 2026-08-30

## [3.0.0] - 2026-08-29

### Added

- **`codex_session(action="steer")`, which corrects a running turn instead of throwing it away.** A delegator watching a turn go the wrong way had one lever, `interrupt`, which loses everything the turn had done. `steer` takes a `prompt` and sends `turn/steer` with the running turn's id as `expectedTurnId`, so another task, a constraint or a directory to leave alone reaches the turn already under way. It answers `{ sessionId, threadId, turnId, status, message }`, and `turnId` is the turn the steer joined rather than a new one — measured on the installed `codex-cli 0.150.1` against a stub holding the model response for 8s and steered at 2s: `turn/steer` answered `{"turnId":"01a04bfa-7f83-…"}`, the id of the turn already running, sent neither `turn/started` nor `turn/completed`, delivered the steered text as a `userMessage` item at +8232ms — the first model round trip after the steer — and made a second upstream request inside the same turn carrying it. So `activeTurnId`, the status and `signalOf` all stand and the turn writes its one `lastResult` at its end: this adds a lever and no state to the session machine, which is why queuing through `thread/queue/*` was not the way to it.
- Codex reads the steered text at the turn's next model round trip and not on arrival, so a steer sent as a turn ends reaches a turn that is over. Both refusals the backend answers with `-32600` — `no active turn to steer` when the turn had ended, ``expected active turn id `X` but found `Y` `` when the session moved on between the caller's poll and its steer — reach the caller as `SESSION_NOT_RUNNING` carrying the backend's own sentence, so the two stay apart and neither reads as a steer that landed. Any other failure of the call is raised as it was: a timed-out request is not a turn that finished.
- A steer moves no field `signalOf` reads, so it wakes no long poll — a woken waiter would answer with the state it already had. It is written to `events.jsonl` as a `progress` record naming `turn/steer` and the turn, because Codex's rollout log carries the `userMessage` item without saying who sent it, and that record is the only place saying this server put text into a turn it did not start.
- **`codex_setup` reports the Windows sandbox, on Windows.** A Windows caller asking for `sandbox: "workspace-write"` against a sandbox that is not set up found out when the turn failed, and `windows/worldWritableWarning` was the only other signal. `windowsSandbox/readiness` answers `ready`, `notConfigured` or `updateRequired` — `codex-schema/v2/WindowsSandboxReadinessResponse.json` requires the field — the call rides the connection `account/read` already opened, and `codex_setup` carries the answer as `windowsSandbox: { status }`, folding `notConfigured` and `updateRequired` into `ready: false` with a warning and a next step. The call is gated on `process.platform === "win32"`: the backend gates it on no platform and the installed 0.150.1 answers `{"status":"notConfigured"}` on Linux, which is the same value a Windows machine with no sandbox gives, so an ungated call would put a permanent false "your Windows sandbox is not configured" into every Linux and macOS report. The MCP server and the app server are always the same machine, so `process.platform` is what decides it.
- **`codex_session(action="terminate_background_terminal")`, which kills one background terminal instead of all of them.** It takes the `processId` a `clean_background_terminals` answer listed, calls `thread/backgroundTerminals/terminate` once, and answers what Codex answered: `backgroundTerminals.terminals: [{ processId, terminated }]`. A process that stayed up reads `terminated: false` — the call reached Codex and the process did not die, which is a measurement and not a failure of the call, so nothing is raised. It lists nothing, so its entry carries no `command` or `cwd` it did not read.
- **A turn that produces no output says why.** `progress.activity` is a scrape of what Codex wrote, so a turn that is blocked, throttled or held by a hook writes no line and a poll answered "running" with nothing to read. Codex CLI 0.150.1 says why on the wire and this server dropped all of it. `codex_check` now answers a `warnings[]` beside `actions[]` — each entry `{ method, message, at }`, oldest first — carrying `warning` and `guardianWarning` free text, a `model/safetyBuffering/updated` whose `showBufferingUi` is true as the model and the reasons named for it, and a `hook/completed` whose run was `blocked`, `failed` or `stopped` as its event name, its status, its status message and the `stop`, `error` and `warning` lines the hook wrote. A new entry wakes a long poll and travels to a held call's `notifications/progress`, because while a turn stalls a warning is the only thing that will be said; the backend repeating the standing one refreshes its instant and wakes nothing. None of it is text this server wrote, so `redactPaths` runs over every message the same as on the error path.
- **A hook's own display line fills the silence before the turn's first marker.** `hook/started` and `hook/completed` carry the `statusMessage` the hook's author wrote — `hooks/list` on the installed 0.150.1 answers one reading `Loading the engineering rules` — and it stands in `progress.activity` while the turn has written no marker of its own. A marker always overwrites a hook line and a hook line never overwrites a marker, and `turn/started` clears both, so each turn starts with the hooks speaking again until Codex does. The activity marker and its instruction are unchanged.
- All five notifications reach `events.jsonl` as `progress` records whatever they do beyond it, including the ones that reach no caller — a buffering the backend marked silent, a hook that held nothing back.
- The volume of this is unmeasured: a `preToolUse` hook fires once per tool call. So a session keeps a ring of the five newest warnings, each cut to 400 characters, and holds one activity line however many hook lines arrive.
- **A session reports the settings it runs with, as `effective`.** `thread/start`, `thread/fork` and `thread/resume` each answer `model`, `modelProvider`, `cwd`, `approvalPolicy` and `sandbox` — required on all three — plus an optional `reasoningEffort`, and that block says what the thread runs with rather than what the call asked for: measured on `codex-cli 0.150.1`, a `thread/start` naming neither model nor provider answered `"model":"gpt-5.6-luna","modelProvider":"myproxy"`. The server records it on the session, writes it to `meta.json`, and answers it from `codex_session(action="get")` and `action="list"`; `effective.cwd` rides with the other sensitive fields. Where the call named a value and Codex answered another, Codex's answer is what the session runs on, and the call's own values stay under `model`, `approvalPolicy` and `sandbox` beside it. A `thread/resume` decides for itself: it restores the thread from Codex's rollout log, so a session picked up by another server reports what that log says, including settings no `meta.json` recorded.
- Only the thread id raises on an answer it cannot read. A settings field the answer does not carry in the shape `codex-schema/v2/ThreadStartResponse.json` gives it leaves the session keeping what the caller asked for and reporting the effective value as unknown — a session runs perfectly well not knowing its model, and no value is invented to fill the gap.
- **`effective` now carries the reviewer and the permission profile Codex settled on, and a listing reports the `permissions` and `approvalsReviewer` the call asked for.** A session started on `permissions: ":read-only"` reported no permission level anywhere: such a call sends no `sandbox`, so the requested field beside `effective` was empty and `effective.sandbox` was a policy object with nothing saying which profile derived it. `ThreadStartResponse`, `ThreadForkResponse` and `ThreadResumeResponse` each require `approvalsReviewer` and offer `activePermissionProfile`, and a live `thread/start` naming `permissions: ":read-only"` on `codex-cli 0.150.1` answered `"activePermissionProfile":{"id":":read-only","extends":null}`. Both are read onto the session, written to `meta.json` and answered by `codex_session(action="get")` and `action="list"`, with `extends` reported only where the profile names a parent. `approvalsReviewer` being required by the schema does not make it load-bearing here — a session runs without knowing its reviewer, so an answer carrying none leaves it unknown like the rest of the block — and the legacy spelling `guardian_subagent` is reported as answered rather than rewritten. Neither is redacted: a profile id names a permission level exactly as `sandbox` does, and carries no path.
- **`permissions` on `codex` and `codex_reply`, so a `[permissions]` profile can be selected from an MCP client.** A user who wrote one in `~/.codex/config.toml` could reach it from nowhere in this server. `permissions` names a profile id — `:read-only`, `:workspace`, `:danger-full-access` or a `[permissions.<id>]` table of their own — and it carries the sandbox and the approval policy that table sets. Measured on the installed `codex-cli 0.150.1`: `permissionProfile/list {}` answers `{"data":[{"id":":read-only","description":null,"allowed":true},{"id":":workspace",…},{"id":":danger-full-access",…}],"nextCursor":null}`, and `thread/start {cwd:"/tmp", permissions:":read-only"}` answers `approvalPolicy "never"`, `sandbox {"type":"readOnly","networkAccess":false}` and `activePermissionProfile {"id":":read-only","extends":null}`. The id travels on `thread/start`, `thread/fork`, `thread/resume` and a `turn/start` that names one, and `meta.json` records it, so a fork and a resume restore the profile the session ran under.
- **`codex_setup` answers `permissionProfiles`**, the ids a call may pass, each with its `allowed` flag and its description. They live there because they are read out of the user's `config.toml` and the project layers under a `cwd`: only a call to the local Codex can name them, while `codex-mcp:///config` and `codex-mcp:///delegation-guide` are static text built from the server's own defaults. Reading them stands up one `codex app-server`. A listing that failed answers `ok: false` with no `profiles` and a `detail` naming the failure, plus a warning and a next step — a listing that did not answer is not a machine that offers no profile.
- **`approvalsReviewer` on `codex` and `codex_reply`, which is what an unattended run can hand its approvals to.** Nobody watches a subagent's approval prompts, and `approvalPolicy: "never"` is not auto-approval: a command needing approval is refused with `approval required by policy, but AskForApproval is set to Never`, so the turn got neither a prompt nor the step. `approvalsReviewer: "auto_review"` routes the request to a Codex subagent that gathers context and applies a risk-based decision framework before approving or denying it, and paired with `on-request` an unwatched turn can step outside its sandbox where the review approves. Verified on the installed `codex-cli 0.150.1`: `thread/start` with `approvalsReviewer: "auto_review"` is accepted and the response echoes `"approvalsReviewer":"auto_review"`, which `ThreadStartResponse` now requires. The field travels on `thread/start`, `thread/fork`, `thread/resume` and every `turn/start`, and `meta.json` records it, so a fork and a resume keep the reviewer the session ran under. `auto_review` is what this server sends; the legacy spelling `guardian_subagent` the schema still accepts is neither published nor sent.
- **A review that did not approve is reported where the caller is already looking.** `item/autoApprovalReview/started`, `item/autoApprovalReview/completed` and `autoApprovalReview/strictReviewRequired` are modelled and taken out of `UNMODELED_SERVER_METHODS`. A completed review becomes an `approval_result` record in the session's `events.jsonl` carrying its `reviewId` and its status, and a status of `denied`, `timedOut` or `aborted` also becomes `progress.activity` — "Approval auto-review denied an action of this turn" — which wakes a held `codex_check(action="poll")`, so the next round says why the turn did what it did. Only `review.status` is read: the schema marks `GuardianApprovalReview` `[UNSTABLE]`, "This shape is expected to change soon", so `rationale`, `riskLevel` and `userAuthorization` reach the log with the raw params and nothing branches on them. Whether a command that would raise `item/commandExecution/requestApproval` under `user` still reaches this server under `auto_review` is unsettled; both hold — an approval request that arrives is answered as it is today, and the review notifications are reported whether or not one does.
- **`progress.activity`: one line saying what Codex is doing right now.** With the event stream gone, a turn running between two approval requests showed a phase, a token counter and nothing about the work. The server now puts a standing instruction on every thread it starts — `thread/start` → `developerInstructions`, which `codex-schema/v2/ThreadStartParams.json` types as an optional string — asking Codex to write `%%%ACTIVITY: <one line>%%%` whenever it starts something new, in the language of the request. The server lifts those lines out of `item/agentMessage/delta`, keeps the last one, and cuts every marker out of `result.text`. It is a heading, not a percentage: how much is done is unknown to the agent and is not reported. One string per session, overwritten — the cost does not grow with the run.
- `advanced.developerInstructions` is appended after the server's instruction instead of replacing it, and `thread/fork` and `thread/resume` carry the same composed string. `CODEX_MCP_DISABLE_ACTIVITY_MARKER=1` sends no instruction; extraction and stripping stay on either way.

### Changed

- **`codex_setup` asks the app server everything it needs on one connection.** The tool paid two process spawns and two `initialize` handshakes for three questions to the same backend: one connection for `account/read` and, on Windows, `windowsSandbox/readiness`, and a second one inside `SessionManager.listPermissionProfiles` for `permissionProfile/list`. A spawn plus `initialize` plus one request measures 37–52 ms on Codex CLI 0.150.1, and it is the whole of what `codex_setup` waits on. The listing now rides the connection the auth probe opened, for the `cwd` the call named, and the order on the wire is `initialize`, `account/read`, `windowsSandbox/readiness` on Windows, `permissionProfile/list`. Each question still answers for itself — a listing that failed leaves the auth state as `account/read` reported it, and an `account/read` that failed leaves the listing to answer — and a connection that never came up is one failure, named once in `warnings`. `SessionManager.listPermissionProfiles` and the `PermissionProfileLister` `executeCodexSetup` took are gone with it; `codex_setup` was the only caller of either.
- **BREAKING: `codex_session(action="clean_background_terminals")` reports what it measured, not that it ran.** It used to answer `{ success: true, message: "Background terminals cleaned for session …" }` after one call to `thread/backgroundTerminals/clean`, whose response schema — `codex-schema/v2/ThreadBackgroundTerminalsCleanResponse.json`, `{"type":"object"}` with no properties — says nothing at all, so the caller was told the terminals were gone whether none, one or ten of them were still running. Codex CLI 0.150.1 carries the two methods that can answer: `thread/backgroundTerminals/list` pages the thread's terminals with a `nextCursor`, and `thread/backgroundTerminals/terminate` answers `terminated: boolean` for one `processId`. The action now lists the thread, terminates each process by id, and lists again, and answers `{ sessionId, backgroundTerminals }`: `terminals[]` — every terminal that was there, with its `command`, `cwd`, `itemId` and `osPid`, the `terminated` Codex answered for it, and `gone`, measured against the second listing — plus `survivors[]`, what was still running at the end, including anything that started during the pass. The cursor is followed to twenty pages and a cursor still standing there answers `truncated: true`. A listing that fails leaves `listError` and no `gone` at all rather than a claim the thread is clear; when it is the first listing that fails — which is what a CLI below 0.150 answers — `thread/backgroundTerminals/clean` still sweeps the thread and the answer carries `cleanCalled: true`, so the caller learns the sweep ran and the state is unknown. Verified against the installed `codex-cli 0.150.1`: `thread/backgroundTerminals/list` on a fresh thread answers `{"data":[],"nextCursor":null}`.
- **BREAKING: `codex-mcp:///server-info` reports `defaultModel` from a value Codex answered, and `defaultModelSource` is gone.** The model was inferred from the most recently active session in memory and published as `defaultModelSource: "session-default"` — a guess dressed as a measurement, and wrong for every session whose model the caller did not name. It is now the model Codex answered a `thread/start` this server sent with no model, which is what a session naming none runs on, and null until such a start has been answered. With one source the source field says nothing the value does not, so it is dropped; null is what unknown looks like.
- **BREAKING: a `codex` call names `sandbox` or `permissions`, one of the two.** `sandbox` was required whenever `CODEX_MCP_DEFAULT_SANDBOX` was unset; a profile carries the sandbox, so the two cannot be combined — `thread/start {permissions:":read-only", sandbox:"workspace-write"}` on `codex-cli 0.150.1` answers ``-32600 `permissions` cannot be combined with `sandbox` ``. The zod schema of `codex` now publishes both as optional and refuses the pair by name, and refuses a call that names neither where the environment sets no sandbox; `codex_reply` refuses the pair the same way. A call that names a profile sends no `-c sandbox_mode=` at all, the environment default included, and a reply that names one over a sandbox session drops the sandbox from the session record rather than carrying both into the next resume. `tools/list` no longer carries `sandbox` in `required`: one-of-two is a rule `required` cannot state, so the parameter descriptions carry it and the schema's own refinement enforces it.
- **An unknown profile id is refused with the ids that exist.** `thread/start` answers one Codex does not know with `failed to load configuration: default_permissions requires a \`[permissions]\` table` — a message about a TOML table the caller never wrote. The id is now held against `permissionProfile/list` first, on the client that is already up and for the cwd of the session, and `codex_reply` runs the same check before the session leaves `idle`. Three answers are told apart: an id in no entry does not exist here and the error names every id that does; an entry carrying `allowed: false` exists and cannot be selected, and says so; and a listing that raised, answered no `data` array, carried an entry without a string `id` and a boolean `allowed`, or handed back more than twenty pages without exhausting its cursor, surfaces as `INTERNAL` naming the reason — the id is not sent on the guess that it is fine.
- **The vendored schema is the bundle `codex-cli 0.150.1` generates.** `codex app-server generate-json-schema --experimental --out codex-schema`, run on 2026-08-29, replaced the bundle CLI 0.106.0 wrote on 2026-02-27. Client request methods went from 52 to 153, server notifications from 41 to 79 and server-to-client requests from 7 to 11 — `attestation/generate`, `currentTime/read`, `item/permissions/requestApproval` and `mcpServer/elicitation/request` are the four that arrived, and `SessionManager.handleServerRequest` answers each with JSON-RPC -32601, so a request this server does not model is refused rather than left to stall the turn. The `v1/` conversation API is down to `InitializeParams` and `InitializeResponse`, and `EventMsg.json` — the schema of the `codex exec --json` event stream — is gone with it, so that stream has no schema in the bundle at all. `tests/protocol-schema.test.ts` records the forty-four server-to-client methods this server does not model — thirty-two of them arrived with this bundle — each with the reason it stays unmodelled, and fails on a method that leaves that list without entering `Methods`.
- **BREAKING: `approvalPolicy` no longer takes `on-failure`.** The app server had already stopped accepting it, so this is not a tightening — it is a parameter that had stopped working. Measured against `codex-cli 0.150.1`: `thread/start {"approvalPolicy":"on-failure"}` answers ``-32600 Invalid request: unknown variant `on-failure`, expected one of `untrusted`, `on-request`, `granular`, `never` ``, and the session failed at the start. `codex` and `codex_reply` take `untrusted`, `on-request` and `never`. Pass `on-request` for a policy that still asks and `never` for one that does not; no preset asks only after a command has failed.
- **`effort` takes any non-empty string.** The schema stopped enumerating reasoning efforts because the set belongs to the model, not to the protocol: on `codex-cli 0.150.1` every entry of `model/list` advertises `supportedReasoningEfforts: low, medium, high, xhigh, max, ultra`, and a closed enum refused `max` and `ultra` before Codex ever saw them. `ReasoningEffort` in `src/app-server/protocol.ts` is a `string`; `codex` and `codex_reply` take any non-empty one, and Codex refuses an effort the chosen model does not advertise, on the turn. `codex-mcp:///server-info` carries the advertised set as `advertisedEffortLevels`, and the two tool descriptions name it.
- **The protocol model carries the names the bundle carries.** The object branch of `AskForApproval` is `granular`, not `reject` — `thread/start {"approvalPolicy":{"reject":{…}}}` on `codex-cli 0.150.1` answers ``-32600 unknown variant `reject`, expected one of `untrusted`, `on-request`, `granular`, `never` `` — and it gained `request_permissions` and `skill_approval`, both left at the schema default `false`: this server sends a preset string and never the granular object. `persistExtendedHistory` on `thread/start`, `thread/fork` and `thread/resume` is `historyMode`, `legacy` or `paginated`; a `thread/start` naming none answers `thread.historyMode: "legacy"`. `ItemNotificationParams` is now two interfaces, `ItemStartedNotificationParams` and `ItemCompletedNotificationParams`, because the schema requires `startedAtMs` on one notification and `completedAtMs` on the other and a single interface would claim a field its notification never sends. `SandboxPolicy` lost `ReadOnlyAccess`: `readOnly` takes `networkAccess` and `workspaceWrite` no longer takes `readOnlyAccess`. A fresh `initialize` is followed at once by an unsolicited `remoteControl/status/changed`, which the server ignores — it drives the child it spawned over stdio.

### Fixed

- **One unreadable field of a `meta.json` no longer hides every session of the state directory.** `codex_session` publishes `approvalPolicy`, `sandbox` and `approvalsReviewer` as zod enums, and the recovered record cast them straight out of `meta.json`, so a value outside an enum failed output validation for the whole `codex_session` answer — one bad session directory took `action="list"` down with it. `approvalPolicy` dropped `on-failure` in this release, so a directory the previous release wrote is exactly such a file. Each of the three is now held against the set the schema names and left out where the value is not in it: the field reports as unknown, which is what a field nothing could read is, and the rest of that session and every other session still list. The narrowing sits where a recovered record becomes a session, so the same values a resume hands back to `thread/resume` are read the same way.
- **`codex_setup` tells a working install it is broken no longer: the auth state comes from `account/read`, not from `codex login status`.** The old probe ran the CLI and matched its English prose with `/not (logged|authenticated)/i`. On a machine whose `~/.codex/config.toml` sets `model_provider` with an `env_key` — the key set, every turn running — `codex login status` prints `Not logged in` and exits 1, and `codex_setup` answered `state: "unauthenticated"`, `ok: false`, `ready: false` for an install that works. ### Added

Shutdown now writes the disk first and synchronously — running sessions as `abandoned`, event logs flushed, claims given up — and bounds each write to the client at one second.
- **`threadId` never reached disk during the first turn.** `meta.json` was written once at creation, before `thread/start` answered, and the next write needed a status change: assigning `threadId` did not qualify. A session killed inside its first turn came back with no `threadId` and no `model`, and a twelve-minute task is exactly one first turn — the worst case was the normal one. Metadata is now written whenever any recorded field changes, so the thread id lands the moment Codex hands it over.
- The recovery scan, the retention prune and the orphan reaper used to act on every session directory they found, including the live sessions of another running server: a second server pruned the first's directories and signalled its codex processes. Each of the three now leaves a session with a live owner alone.

### Removed

- The in-memory event buffer, with its cursors, its pinning, its soft and hard eviction limits, its delta coalescing and its byte-budget truncation. A session holds its status, its open requests, its progress counters and its last result. The events of a turn are written to `events.jsonl` under the state directory as before, and a restart reads that file only for the sequence number to continue from.
- **BREAKING: the `STATE_DIR/.lock` lockfile.** One global lock for a whole state directory was never the unit of exclusion: a session is driven by one client through one server, so the lock belongs on the session. What the global lock actually did was silence the second client — no session of its reached the disk, and it listed none of the first client's. `src/persistence/lockfile.ts` is gone; a `.lock` left by an older build is ignored.

## [2.2.0] - 2026-08-26

First release of this fork. It carries the 2.1.1-2.1.7 work published on npm by @leo000001,
reconstructed from the sourcemaps of those packages, and adds the fixes and tests below.

### Fixed

- An answer a caller marked secret stays out of the log. `ToolRequestUserInputQuestion.isSecret` marks a question whose answer is a secret, and `resolveUserInput()` put the answers straight into the event buffer and `events.jsonl`. The answer reaches codex as given; the log records `<secret>`.
- The client asks for the `experimentalApi` capability. It sent `clientInfo` alone, so the connection ran with the schema default of `false` — and the schema marks `item/tool/requestUserInput` and `item/plan/delta` as experimental. The whole user-input path in the manager served requests the backend never sent.
- An `exec` turn keeps the answer the CLI gave it. `EventMsg.json` carries the reply in `agent_message`, which the event table did not map at all, and in `task_complete.last_agent_message`, which nothing read — so a legacy stream, the very reason exec mode exists, finished a turn with an empty answer.
- Command output is visible in exec mode. `ExecCommandOutputDeltaEventMsg` names the payload `chunk` while the app-server notification names it `delta`, so the noise filter, the delta coalescing and the compact response found nothing. The exec client now hands over the shape the app-server schema declares, and renames it only when the CLI sent a string, since the schema types those bytes as possibly not UTF-8. `agent_message_content_delta`, `plan_delta`, both reasoning deltas and `agent_reasoning_section_break` carried the same snake_case mismatch.
- An interrupted `exec` turn reports `interrupted`, a status `TurnStatus` defines; it reported `cancelled`, which the protocol does not carry.
- `context_compacted` and `deprecation_notice` reach the client from exec mode. Both exist in `EventMsg.json` and both have handlers, but the event table dropped them as unknown. Four keys of that table named events the schema does not define at all.
- `thread/started` reports the thread status. `Thread.status` is an object union, and the code read it as a string, so the field was empty every time.
- `progress.percent` is gone. Nothing in the bundle carries a per-turn percentage — the only percent is the account rate-limit window — so the field was promised to clients and never filled. The tests that covered it emitted payload shapes the schema does not define; they now emit what the schema says arrives.
- The token counters of a finished turn no longer outrank a later `thread/tokenUsage/updated`.
- `rawResponseItem/completed` is parsed as the `ResponseItem` it carries. It was matched against `agentMessage` and `text`, which belong to the `ThreadItem` hierarchy, so the branch was false in both modes.
- `extractThreadId()` and `extractTurnId()` no longer accept a top-level `threadId` or `turnId`. No response in the bundle carries either — v1 answers `conversationId`, v2 answers `thread` and `turn` — and a test pinned the shape that never existed.
- An answer to an approval request now fails when it could not be written. `AppServerClient.respondToServer()` swallowed the write error and returned, so the rollback in `resolveApproval()` was unreachable: a `decline` lost to backpressure was reported to the caller as delivered, the request left the pending map, the session went back to `running`, and codex waited for an answer that never came until its TTL expired.
- A lock held by a live process of another user is no longer reclaimed. `isPidAlive()` read every `process.kill(pid, 0)` failure as death, but the kernel raises `EPERM` for a process that is alive and owned by someone else, so a second server on a shared `STATE_DIR` deleted the first server's lock and both wrote to the same session directory. A lockfile that carries no readable pid is left alone as well.
- A recovered session keeps the timestamps it was stored with. `ingestRecovered()` stamped `lastActiveAt` with the current clock and wrote it back to disk, and retention selects directories by that field — so a session cut off mid-run grew younger at every restart and was never pruned by age. It no longer invents `cwd` either, and a status it cannot read now carries the reason.
- The orphan reaper terminates the process group, as ordinary cleanup does. Both clients spawn codex detached and signal `-pid` when they shut down, but the reaper signalled the leader alone and `taskkill` without `/T`, so commands and background terminals outlived a reap that reported success. The group is signalled only when the recorded pid leads its own group, read from the same snapshot as the start time.
- `ReapSummary.reaped` counts confirmed exits. It counted attempts: a process that ignored `SIGTERM` where no source could answer for its identity was reported as reaped. Signalled processes whose exit could not be confirmed are counted separately, and the startup log names them.
- A failed filesystem read reaches the caller instead of passing for an empty directory. `scanRecoverableSessions()` and `pruneSessionDirs()` answered `[]` and `0` when they could not list the state directory; `existsSync()` reports `false` on `EACCES` too, so the check itself hid the refusal. A session whose `meta.json` cannot be parsed is now recovered from what the directory itself states rather than dropped, which keeps its `pid.json` reachable for the reaper.
- `codex_reply` reports the overrides that did not take effect. `codex exec resume` accepts no `-s`, `-C` or `--output-schema`, and the request answered with plain success: narrowing a session to `read-only` on a later turn left codex writing under `workspace-write`. The unapplied overrides now reach the caller through `compatWarnings`, and a dropped `outputSchema` also clears the schema-constrained mark.
- An `exec` turn no longer reports success it cannot back. A process that exited zero without a single recognised event, or one that lost a JSONL line and would otherwise hand back the previous turn's text as final, completes as `failed` and says how many records were lost. A schema that could not be written now fails the turn instead of starting it without `--output-schema`, and `threadBackgroundTerminalsClean()` refuses in exec mode instead of answering `{}` to a caller told the terminals were cleaned.
- A probe that never answered is no longer read as "this CLI has no app-server". A five-second timeout and a spawn failure both meant `exec` for the life of the process — approvals gone, `fork` and `resume` refused — and a restart made it go away without explaining anything. The timeout is retried once with a longer budget, and each outcome says which one it was.
- The compat report states whether disk persistence is actually on. It was hardcoded to `true`, so a server running from memory told clients their sessions would survive a restart. `serverInfo` no longer assumes `app-server` for the backend either, and `codexCliVersion` reports nothing rather than the first word of an error message.
- `codex_setup` answers `ready: false` for an auth state it could not classify; it treated anything other than an outright `unauthenticated` as good enough.
- Restored events keep the timestamps from the log; a line without one is dropped and counted rather than stamped with the time of the restart.
- Persistence failures are visible. Writes of session metadata, results and `pid.json`, and the removal of a session directory, each failed in silence: a lost `pid.json` left a codex process nothing would reap, and `codex_session action=clean` reported a removal that had not happened.
- A server whose state directory cannot be created starts without persistence instead of exiting. The `SessionPersistence` constructor throws from `mkdirSync` before the fallback could apply.
- Recovery no longer returns sessions that pruning has already deleted.
- A server that cannot take the `STATE_DIR` lock runs from memory instead of touching the state directory another server owns. It previously warned and carried on: it recovered the other server's sessions, pruned their directories, and handed their live PIDs to the orphan reaper, which then killed the running codex processes of the first server.
- The orphan reaper confirms process identity by start time before it signals anything. Its `/proc` path compared no times at all and treated every live PID as an orphan when the recorded spawn time was under a day old, so a process that inherited a reused PID was killed. Where no source reports a start time, the process is left alone.
- The orphan reaper reads process creation time through `Get-CimInstance` on Windows, falling back to `wmic`. `wmic` ships disabled on Windows 11 24H2 and is absent from Server 2025, which left identity unverified. The `wmic` path also read its local timestamp as UTC and ignored the offset, so identity never matched off UTC.
- Session events reach `events.jsonl`. `appendEvent()` was called from nowhere, which left the event log dead code and the recovery scanner reading a file that never existed; `ingestRecovered()` also dropped the events it had just read. A recovered session now carries its events back, and its buffer ids continue the sequence written to disk.
- `forkSession()` writes `meta.json` and `pid.json` for the fork. The fork's directory was invisible to recovery and its child process invisible to the reaper.
- Retention measures a session directory in full. `getDirSize()` counted only top-level files, so a session whose bytes sat in subdirectories weighed zero and the disk limit never applied.
- A corrupt line in the middle of `events.jsonl` no longer discards every valid event after it. The count of skipped lines reaches the caller and stderr; a torn last line stays silent, since that is what a power cut leaves.
- `pid.json` records the model under `model`. It was written under `command`, a field no reader used.
- Path redaction applies to `error.message`, not only to a bare string. Real app-server errors always carry the object form, so redaction had never run on them.
- `ExecClient` reports errors in one shape, the `TurnError` object the protocol schema defines. It previously alternated between a bare string and an object, and retryable errors carried in `error.message` were read as terminal.
- `thread/status/changed`, `thread/closed`, `thread/compacted`, `deprecationNotice` and `configWarning` reach the client instead of falling into `default: break`. Session status stays governed by the pending-request map, so a status notification that arrives before its approval request, or after the answer, cannot strand a session.
- `check:stdio` waits 6 s for the server to exit on its own, up from 2 s. The old window killed the child on a cold runner and reported the kill as a runtime failure.
- An event carries one timestamp. `pushEvent` and `appendEvent` each read the clock, so the two disagreed across a millisecond boundary and a restored session handed the client a timestamp it had never polled. `appendEvent` now takes the timestamp and reads no clock of its own.
- A cancelled session answers `CANCELLED`. `replyToSession`, `interruptSession`, `cleanBackgroundTerminals` and `forkSession` looked the client up before they checked the status, and cancelling a session removes its client, so the caller was told `SESSION_NOT_FOUND` — the code for a session that never existed.

### Added

- The documents the server hands its clients are checked against the schema bundle on every test run: a field path a resource names must resolve in a tool schema or in `codex-schema/`, so a promise the backend does not back fails the build. `initialize` is checked the same way — the capabilities the client actually writes to stdin are read back and matched against `InitializeParams`.

The `delegation-guide` names all six effort levels, including `none` and `minimal`, and states the level a rejected `minimal` turn is retried at.
- The compat report distinguishes `diskPersistence` from `diskResume`: sessions survive a restart as history, and a recovered session has no codex process behind it.
- CI runs `check:stdio` and `smoke:mcp` across the matrix — the only checks that start the server and exercise the lock, recovery, reaping and stdout cleanliness. A separate job runs `rumdl` over the markdown, which nothing linted before.

- Tests: 98 to 907, line coverage 60.7% to 98.5%. Modules that arrived in 2.1.1-2.1.7 with no tests at all - persistence primitives, session persistence, orphan reaper, backend detection, exec client, `codex_setup`, executable resolution, foreground execution, turn compatibility, stdin shutdown - are covered, along with the MCP tool surface, the JSON-RPC client and the resource documents.

## [2.1.5] - 2026-04-05

### Added

- **Disk persistence** — session metadata (`meta.json`), event logs (`events.jsonl`), and results (`result.json`) are now persisted to `~/.codex-mcp/state/` (configurable via `CODEX_MCP_STATE_DIR`). Surviving sessions are recovered on server restart with status `error` (reason: `server_restart`); completed results remain queryable.
- **Graceful shutdown with stdin drain** — when the MCP client disconnects (stdin closes), the server now waits up to 15 s (Windows) / 10 s (Unix) for active sessions to complete before forcing shutdown, matching claude-code-mcp behavior.
- **Orphan process reaper** — on startup, detects and terminates leaked `codex app-server` child processes from previous crashed server runs using PID + spawn-timestamp identity verification (cross-platform: `wmic` on Windows, `ps`/`/proc` on Linux).

- **TTL warning events** — sessions approaching idle/running TTL expiry receive a `codex-mcp/ttl_warning` progress event 60 s before cleanup (emitted once per session).
- **STATE_DIR lockfile** — prevents multiple server instances from corrupting the same state directory.
- **Tiered flush strategy** — critical events (approvals, results, errors) are flushed to disk immediately; progress/output events are batched every 100 ms.
- **Three-dimensional retention policy** — old sessions are pruned by age (7 days), count (200), and disk size (500 MB).
- **`codex_setup` tool** — reports codex executable, auth and app-server readiness.
- **Foreground execution** (`src/utils/execution.ts`) — `codex`/`codex_reply` can wait for a result instead of returning immediately.
